# Twemoji Resurrection 功能与架构审查

审查日期：2026-10-15。基线：本地 `97e3ada`，模块显示 v17.0.3 (58)。范围为当前工作区及本地同名发行 ZIP，不代表已核验 GitHub 在线发行资产。未修改 `module/`，未操作设备或发布渠道。

## 结论

保留现有 systemless 字体替换路线。预启动阶段替换 CBDT/CBLC 字体、沿用管理器模块生命周期、无需 Zygisk，对这个体量的项目是合理选择。问题集中在配置识别、自检可信度与接口集成，不需要重写为 App 或引入常驻进程。

发现 6 项可复现的功能问题：1 项 P1、5 项 P2。其中解析器既可能漏选 emoji 字体，也可能误选普通字体；自检复用同一份错误槽位清单，会把遗漏隐藏为“全部生效”。WebUI 实时自检目前还有两个相互独立的阻断问题。应先修解析目标与诊断链，再考虑扩展功能。

## 发现（按严重度）

### R1 / P1：sed 的 family 范围可能吞入普通字体族

位置：`module/post-fs-data.sh:25-27`；同样的表达式存在于 `module/install.sh:55-57`、WebUI 的 CHECK_CMD。

合法 XML 不要求标签独占一行。以下输入会让 sed 的范围延续到下一个 family 的结束行：

```xml
<family lang="und-Zsye"><font>NotoColorEmoji.ttf</font></family>
<family lang="en">
  <font>Other.ttf</font>
</family>
```

隔离执行原始启动脚本的解析与挂载逻辑后，`Other.ttf` 也被替换为测试 emoji 字体，描述为 `active (2/2)`。如果误选的是正文所需字体，可能导致普通文字渲染异常。此为构造的有效配置复现，未声称某台实际设备已出现该排列。

同一表达式还有反向遗漏：font 的起止标签跨行时提取不到文件名；同一行有两个 font 时只提取最后一个，甚至报告 `active (1/1)`。三个样本均已复现。

建议：按 XML 元素边界识别 family/font，正确处理跨行、同一行多标签及嵌套元素；只允许经过验证的目标进入安装链接与挂载清单，不能把按行正则结果直接作为改写系统字体的依据。

### R2 / P2：配置优先级与 Android 实际使用的配置不一致

位置：`module/post-fs-data.sh:25-26`；`module/install.sh:55-56`；`module/webroot/index.html:134-135`。

只要 `fonts.xml` 解析出任一槽位，就完全忽略 `font_fallback.xml`。AOSP Android 15 的选择受 `newFontsFallbackXml` 标志控制，当前主线使用 `font_fallback.xml`；“旧文件非空”不等于系统正在使用旧文件。

复现：旧文件只有 Noto，新文件还有 Vendor；脚本只替换 Noto，Vendor 保持原厂内容，自检却显示 `active (1/1)`。影响使用新配置且两份槽位清单不一致的 ROM；两份配置相同的设备不受这个差异影响。

建议：对齐系统生效配置，并披露解析来源；对于无法确认的 ROM，明确诊断覆盖范围，避免把仅命中旧配置解释为全系统验证成功。

### R3 / P2：WebUI 自检命令拼接出 shell 语法错误

位置：`module/webroot/index.html:130-142`。

数组用 `'; '` 连接后得到 `for ...; do; if ...; then; ...`。实际取出网页 CHECK_CMD 交给 `bash -n`，返回语法错误。`do` / `then` 后的空命令不合法，任何能够正常执行此命令的桥接仍会遇到这一问题。

建议：按完整 shell 语句组织命令，或通过统一诊断脚本输出机器可读结果；检查退出码与 stderr，避免静默掩盖执行失败。

### R4 / P2：WebUI 错把原生 KernelSU exec 返回值当对象

位置：`module/webroot/index.html:169-174`、`194-199`。

官方 Kotlin 原生 `exec(cmd: String)` 返回 String；npm JS 包装器才将 callback API 包成 `{ errno, stdout, stderr }` 的 Promise。页面没有导入该包装器，直接 `await ksu.exec(cmd)`，却只读 `r.stdout` / `r.result`。

以官方单参数接口的字符串返回形式模拟，即使返回合法的逐槽 OK 结果，也被丢弃。降级读取 module.prop 同样被丢弃，最终显示 `installed`，版本空白。它与 R3 独立：只修命令仍不能在此原生接口上正确工作。

建议：集中封装管理器桥接，对返回类型和错误状态进行明确适配；同时覆盖实时自检与 module.prop 读取。

### R5 / P2：安装版本与更新清单 versionCode 不一致

位置：`module/module.prop:4`、`module/update.json:3`。

显示版本为 build 58，模块安装码仍为 57，而更新清单是 58。本地发行 ZIP 中也确认是 57。管理器按 versionCode 比较时，安装此 ZIP 后仍会认为存在 58 更新，重复提示安装相同构建。

建议：发布元数据由单一来源生成，打包前检查版本码、显示版本、banner、changelog、更新 URL 的一致性。在线 Release 标题/正文和资产仍需另行核对。

### R6 / P2：Intl.Segmenter 缺失会中断整个页面初始化

位置：`module/webroot/index.html:104-105`。

项目未规定 WebView 最低能力，但直接构造 Intl.Segmenter，且在状态自检启动之前。模拟一个不提供此 API 的 WebView 后抛异常，画廊构建与自检均中止，状态会停留在初始 checking 文案。

建议：功能检测并提供能保持 emoji 序列的降级数据或分段方式；画廊初始化失败不应阻断诊断。没有据此断言某个 Android 版本必定缺失此 API。

## 架构中需要收紧的边界

1. **挂载与验证共用一份解析清单，会产生共同盲区。** R1、R2 已证明“清单里全成功”不能直接等同于“系统全部 emoji 生效”。至少应报告配置来源、解析失败、实际目标路径和未覆盖来源。
2. **字体来源不止 `/system/fonts`。** AOSP 还读取 `/product/etc/fonts_customization.xml`、`/product/fonts`，并支持由 updatableFontMap 指向 `/data/fonts/files` 的更新字体。当前脚本只验证 system 槽位。此为源码确认的覆盖边界，尚未在存在这些 emoji 覆盖源的设备上做端到端复现，不能直接宣称所有 OEM/字体更新路径都已支持。
3. **Magisk 时序说明有误。** 官方说明 module post-fs-data 脚本在模块挂载前运行。代码/README 将其描述为 Magic Mount 已完成、cmp 守卫自然成为 no-op，并不符合该顺序。尚未据此证明 bind-mount 与后续 Magic Mount 必然冲突；需要实际冷启动验证，最终状态应在管理器挂载完成后复核。替换动作仍需保留在字体缓存建立前。
4. **安装、启动、WebUI 重复实现解析与检查。** 建议提取一个共用诊断/目标发现入口，前端只消费结构化结果；安装与启动保留各自生命周期职责。
5. **发布和自测缺少可重复入口。** 审查前无跟踪的 tests、打包脚本、自动版本一致性门禁，也没有 project_status.md。仅靠手工清单已实际漏掉 versionCode。

推荐沿现有路线做集中加固；本次没有实施架构调整。优先顺序为 R1/R2 → R3/R4 → R5/R6，再补真实管理器安装与启动回归。
